# Demo – Vibe Coding einer App

**Vibe Coding** ist ein moderner, KI-gestützter Ansatz der Softwareentwicklung, bei dem Sie in einfacher Sprache beschreiben, was Sie wollen, und ein generatives KI-Tool – wie Databricks Genie Code – die Anwendung schnell für Sie aufbaut (Scaffolding). Statt von einer leeren Datei zu starten und Boilerplate von Hand zu schreiben, iterieren Sie im Gespräch: eine Idee beschreiben, die Ausgabe prüfen, Probleme aufzeigen und Ihre Prompts verfeinern, bis die App sich wie beabsichtigt verhält.

In dieser Demonstration verwenden Sie Genie Code innerhalb von Databricks Apps, um eine einfache Datenanwendung von Grund auf zu prototypisieren, wobei Best Practices für die Produktionalisierung der App hervorgehoben werden. Sie legen bewusst gängige Probleme offen, die während der KI-gestützten Generierung auftreten, und üben Prompt-Engineering-Techniken, die zu Ergebnissen höherer Qualität führen. Dieser Workflow spiegelt wider, wie Enterprise-Entwickler zunehmend interne Werkzeuge auf der Databricks-Plattform bauen – schnell, iterativ und mit KI als Co-Pilot.

## B. Einführung

In diesem Abschnitt führen wir das Konzept des Vibe Coding ein und erkunden, wie es mit Genie Code angewendet werden kann. Genie Code bietet zwar eine bequeme und leistungsfähige Umgebung für diesen Workflow, aber die behandelten Prinzipien sind nicht auf ein bestimmtes Tool beschränkt.

Bei Vibe Coding geht es grundlegend darum, wie Sie mit KI interagieren, um Software zu entwerfen, zu generieren und zu verfeinern. Dieser Workflow lässt sich gleichermaßen gut über verschiedene Plattformen, IDEs und Modelle hinweg anwenden. In dieser Demo verwenden wir Genie Code als Scaffolding-Plattform, um diese Fähigkeit aufzubauen, mit einer Databricks App als Ziel.

### B1. Was ist Vibe Coding?

Vibe Coding ist ein KI-zuerst-Entwicklungsstil, bei dem der Entwickler die Absicht beschreibt (die „Vibe" der Anwendung) und ein KI-Modell den entsprechenden Code generiert. Die Rolle des Entwicklers verschiebt sich vom Schreiben von Syntax zum Anleiten, Prüfen und Verfeinern der generierten Ausgabe. Es ist ein iterativer Prozess: eine Idee beschreiben → Code generieren → testen und prüfen → verfeinern und erneut prompten – wiederholt, bis die App sich wie beabsichtigt verhält.

#### B1.1 Vergleich zur traditionellen Entwicklung

Traditionelle Entwicklung beginnt mit einer leeren Datei und erfordert, dass der Entwickler den vollständigen Implementierungspfad kennt. Vibe Coding beginnt mit einer Beschreibung und erfordert, dass der Entwickler weiß, wie er das Ergebnis bewertet und steuert. Das bringt viele offensichtliche Vorteile:

- **Geschwindigkeit – Schnelles Prototyping:** Kommen Sie in Minuten von der Idee zum funktionierenden Entwurf, statt von einer leeren Datei zu starten.
- **Effizienz – Boilerplate reduzieren:** Lassen Sie die KI das wiederholte Setup und die Framework-Verrohrung übernehmen, damit Sie sich auf die Absicht konzentrieren können.
- **Lernen – Unbekannte Frameworks erkunden:** Beschreiben Sie, was Sie brauchen, ohne APIs auswendig zu lernen, und prüfen und verfeinern Sie dann, was das Modell produziert.

> **Wichtigste Erkenntnis**
>
> Beide Fähigkeiten sind wertvoll. Vibe Coding beschleunigt den ersten Entwurf und die folgenden Wiederholungen, aber Engineering-Urteilsvermögen steuert den Prozess und formt damit das Endprodukt.

### B2. Was ist Genie Code?

**Genie Code** ([AWS](https://docs.databricks.com/aws/en/genie-code/) | [Azure](https://learn.microsoft.com/en-us/azure/databricks/genie-code/) | [GCP](https://docs.databricks.com/gcp/en/genie-code/)) ist Ihr KI-Partner für Datenarbeit, eingebettet im gesamten Databricks-Workspace – einschließlich Notebooks, SQL-Editor, Lakeflow, Dashboards und ML-Workflows. Es kann Python und SQL generieren, erklären, optimieren und debuggen.

Im Kontext von Databricks Apps können Sie eine Anwendung in natürlicher Sprache beschreiben und einen funktionierenden Entwurf erhalten, der Layout, Datenverbindungen und Interaktivität umfasst.

- **App-Scaffolding aus Prompts:** Generieren Sie eine funktionierende Anwendungsstruktur aus einer einzigen Beschreibung in natürlicher Sprache.
- **Databricks-bewusster Kontext:** Versteht Catalogs, Schemas, Tabellen und SQL Warehouses ohne zusätzliche Erklärung.
- **Ausführbarer Python-Code:** Erzeugt lauffähigen App-Code, der sich direkt in die Plattform integriert.
- **Iterative Verfeinerung:** Erweitern, anpassen oder reparieren Sie die App über Folge-Prompts, ohne von vorne zu beginnen.

## C. Eine einfache App prototypisieren

In diesem Abschnitt gehen wir vom Konzept zur Umsetzung über, indem wir eine Anwendungsidee zum Leben erwecken. Hier beginnt der Vibe-Coding-Prozess – mit einer einfachen Idee starten, sie in einen Prompt übersetzen und mit KI ein erstes funktionierendes Scaffold generieren.

Das führt uns durch die frühen Phasen des Workflows:
- die App definieren
- die erste Version des Codes generieren
- sie zum Laufen vorbereiten
- den Code in eine App deployen

Das Ziel ist nicht, beim ersten Versuch eine perfekte Anwendung zu produzieren, sondern einen soliden Ausgangspunkt zu etablieren, auf dem wir iterieren und verfeinern können.

### C1. Die App-Idee definieren

Vor dem Prompten hilft es, klar zu artikulieren, was die App tun soll. Eine gut abgegrenzte Idee umfasst vier Elemente:

| Element | Frage |
| --- | --- |
| **Zweck** | Welches Problem löst die App, oder welche Frage beantwortet sie? |
| **Datenquelle** | Unity Catalog? Lakebase? Aus welcher Tabelle liest die App? |
| **Benutzerinteraktion** | Welche Eingaben liefert der Benutzer, und welche Ausgabe sieht er? |
| **Format** | Wie wird die Ausgabe angezeigt? Tabelle, Chart, Filterpanel oder eine Kombination? |

Für diese Demonstration lautet die App-Idee:

> Baue eine einfache App, die es dem Benutzer erlaubt, eine Tabelle in Unity Catalog anzusehen und grundlegende CRUD-Operationen darauf durchzuführen.

Das ist spezifisch genug, damit Genie Code einen sinnvollen ersten Entwurf generiert, aber einfach genug, um innerhalb der Demo-Zeit abgeschlossen zu werden.

### C2. Den initialen Prompt an Genie Code senden

Mit einer Idee im Kopf erwecken wir sie mit Genie Code zum Leben! Für Demo-Zwecke beginnen wir bewusst mit einem recht einfachen Prompt, um zu sehen, wohin uns das bringt, und folgen dann von dort aus dem Vibe-Coding-Workflow:
- den generierten Code testen und prüfen
- basierend auf unseren Beobachtungen nach Bedarf wiederholen und verfeinern

> Dieser Ansatz spiegelt wider, wie Vibe Coding in der Praxis funktioniert – das erste Ergebnis ist ein Ausgangspunkt und sollte immer als Entwurf oder vorgeschlagene Implementierung betrachtet werden – nicht als fertiges Produkt.

1. Öffnen Sie einen Prompt, indem Sie oben rechts auf der Seite auf das Symbol **Genie Code** klicken; das öffnet das Genie-Code-Panel auf der rechten Seite.
1. Geben Sie einen Prompt ein. Für diese Demo haben wir verwendet:

> Please write an app that allows me to view a UC table and edit, add and delete rows. Write the app source in a folder named "vibe_app" in my user home folder. Do not actually create the app; I will deploy the source to an existing app.

> Dieser Prompt ist einfach genug, artikuliert aber klar, wo der Quellcode erstellt werden soll, und ist konkret darin, keine App zu erstellen.

3. Genie Code macht sich an die Arbeit und fragt Sie im Verlauf nach Bestätigung verschiedener Aktionen. Klicken Sie auf **Allow**, um fortzufahren.
   - Sie können auch die Option **Always Allow** wählen, um nicht jedes Mal gefragt zu werden.
   - Sie werden weiterhin aufgefordert, Aktionen zu **Run**, die Genie Code als riskant einstuft (z. B. Dateimanipulationen).
4. Wenn Genie Code fertig ist, klicken Sie auf **Accept all**, um die generierten Assets zu übernehmen.
5. Navigieren Sie zu Ihrem Ordner **vibe_app**, um die von Genie Code erstellten Dateien zu erkunden.

> **Hinweis**
>
> Da LLM-Ausgaben variieren können, haben wir eine Version der generierten App beigefügt, um eine konsistente Basis zu erfassen; sie befindet sich im Unterordner **vibe_app**; verwenden Sie den Datei-Navigator links, um auf den mitgelieferten Quellcode zuzugreifen. Das ist die Version der App, die wir in dieser Demo besprechen, aber erkunden Sie ruhig und vergleichen Sie mit Ihren eigenen Ergebnissen.

### C3. Überblick über den generierten Code

Die generierte App folgt dem allgemeinen Muster einer minimalen Databricks App und besteht aus drei Dateien:

| Datei | Beschreibung |
| --- | --- |
| `app.py` | Der Hauptteil des Anwendungsquellcodes, der eine Streamlit-UI und einen dünnen Databricks-Client implementiert. |
| `app.yaml` | Definiert, wie die App deployed wird, einschließlich Startverhalten und Umgebungskonfiguration. |
| `requirements.txt` | Listet Python-Pakete und ihre Versionen auf, die in die Laufzeitumgebung installiert werden. |

> Alle Apps brauchen eine YAML-Datei (damit Databricks weiß, wie Ihre App zu starten ist) und eine `requirements.txt` (damit Laufzeitabhängigkeiten erfüllt werden können), aber es besteht Flexibilität darüber, wie die Python-Teile organisiert sind. Komplexe Apps können über mehrere Dateien oder Module aufgeteilt werden.

Ein kurzer Blick auf den App-Quellcode sagt uns, dass diese App ein SQL Warehouse benötigt. Intuitiv ergibt das Sinn, da sie SQL-Workloads ausführen können muss, um Tabellen zu laden/speichern. Konkret erwartet sie, eines über die Umgebungsvariable `DATABRICKS_HTTP_PATH` zu entdecken.

Leider passt das nicht ganz dazu, wie die Dinge funktionieren, wenn Sie ein SQL Warehouse als Ressource zu einer App hinzufügen; die Nutzung dieses eingebauten Mechanismus liefert die **Warehouse-ID**, nicht ihren **HTTP-Pfad**.

Diese Lücke hebt etwas Wichtiges am Vibe-Coding-Prozess hervor:

> Fehlende Details im Prompt → Modell trifft Annahmen, um Lücken zu füllen → nicht erfüllte Erwartungen

Ohne klare Einschränkungen oder Details im Prompt treffen Modelle Annahmen. Oft haben wir Glück und diese Annahmen wirken zu unseren Gunsten. Aber manchmal führen sie zu Fehlausrichtungen wie dieser (oder schlimmer).

In diesem Fall war die fehlende Einschränkung etwas wie *Stelle sicher, dass alle benötigten Ressourcen über Standard-App-Ressourcen und die YAML-Datei bereitgestellt werden können.*

An diesem Punkt gibt es ein paar Wege, das Problem zu lösen:
- Wiederholen (erneut prompten, um den Code zu verfeinern und das Problem zu beheben), was wir später in der Demo behandeln
- Die Lücke durch Code- oder Konfigurationsänderungen schließen. Wir verwenden hier diesen Ansatz, da er ein gutes Beispiel für die Dinge ist, die wir früh im Vibe-Coding-Lebenszyklus oft tun müssen.

### D2. Den Code inspizieren

An diesem Punkt wissen wir, dass diese App nicht perfekt ist. KI-generierte Apps sind es beim ersten Durchlauf selten. Wir haben bereits zwei Probleme aufgezeigt und fangen gerade erst an. Jetzt ist es Zeit, den Code kennenzulernen. Als derjenige, der für die Auslieferung einer Anwendung verantwortlich ist, sind Sie der Architekt (nur nicht der Tippende). Also _müssen Sie verstehen, was der Code tut_.

- Sie müssen verifizieren können, dass er sich korrekt, sicher und vorhersehbar verhält.
- Modelle generieren einfach Code basierend auf statistischen Mustern, nicht auf Verständnis.
- Wenn Sie eine KI-generierte App produktionalisieren, die Sie nicht verstehen, dann spielen Sie buchstäblich Glücksspiel.

> **Immer bedenken**
>
> Vibe Coding ist eine Ergänzung zu soliden Softwareentwicklungspraktiken – kein Ersatz.

#### D2.1 Gängige Fehlermuster

Beim Prüfen von Code (und das gilt besonders für KI-generierten Code) müssen Sie in Fehlermodi denken. Die natürliche „Hat es funktioniert?"-Denkweise, die in dieser Phase verbreitet ist, muss durch „Wie könnte das in der Produktion kaputtgehen?" ersetzt werden.

Die folgenden Kategorien von Problemen treten häufig in Apps auf, die mit Genie Code oder ähnlichen KI-Coding-Tools generiert werden:

**Daten & Logik**
- **Halluzinierte Spalten- oder Tabellennamen** – das Modell erfindet Elemente, die nicht existieren.
- **Falsche Filterlogik** – Bedingungen können die falschen Operatoren, Datentypen oder Annahmen verwenden, besonders bei Datumsangaben und NULL-Werten.
- **Hartcodierte Werte** – statische Werte werden eingebettet statt parametrisiert.
- **Missbrauch von APIs** – generierter Code kann SDKs oder Connectoren auf subtile, aber falsche Weise verwenden.

**UX & Ablauf**
- **Layout-Fehlanpassungen** – UI-Komponenten spiegeln nicht den beabsichtigten Benutzerablauf oder das mentale Modell wider.
- **Fehlende Fehlerbehandlung** – leere Ergebnisse, NULL-Werte und fehlgeschlagene Operationen werden oft ignoriert.
- **Stille Fehlermodi** – Fehler werden verschluckt oder ignoriert, was zu irreführendem Verhalten führt.
- **Blockierende / synchrone Annahmen** – lange Operationen laufen inline ohne Status, Fortschritt oder Feedback.

**Sicherheit & Zuverlässigkeit**
- **Verletzungen von Vertrauensgrenzen** – Benutzereingaben treiben direkt Queries, Aktionen oder Ressourcenauswahl.
- **Zu freizügiges Verhalten** – die App erlaubt uneingeschränkte Operationen oder zu breiten Zugriff auf Daten oder Ressourcen.
- **Fehlende Idempotenz** – wiederholte Aktionen können doppelte Inserts, Ressourcenerstellung oder andere unerwünschte Nebeneffekte auslösen.
- **Fehlende Observability** – kein Logging, Tracing oder nützliche diagnostische Informationen werden erfasst.

Die meisten dieser Probleme sind **auf den ersten Blick nicht offensichtlich**, was sie genau so gefährlich macht. Sie schnell zu erkennen ist eine Kernfähigkeit in der KI-gestützten Entwicklung.

#### D2.2 Beispiele für Fehlermuster

Bisher sind wir in unserer App auf Folgendes gestoßen:
- eine Fehlanpassung, wie die App das SQL Warehouse entdeckt versus wie die Plattform es der App bereitstellt, was ein **Daten & Logik**-Problem veranschaulicht (Missbrauch von APIs)
- das Verpatzen der Konvertierung von Datums-/Zeitwerten beim Zurückschreiben von Daten, was ein weiteres **Daten & Logik**-Problem veranschaulicht (falsche Filterlogik)

Bei der Untersuchung des App-Quellcodes dauert es nicht lange, bis wir mehr entdecken:

Das Einbetten von `table_name`, dessen Wert aus einem Eingabefeld stammt, in einen SQL-Query-String stellt ein Risiko der SQL-Injection dar, was ein ernstes Sicherheits- und Zuverlässigkeitsproblem darstellt. Das ist eine Verletzung der Vertrauensgrenze, die behoben werden muss.

## E. Iterieren und Verfeinern

Beim Vibe Coding ist die erste Ausgabe ein Entwurf – immer. Iteration ist nicht optional – sie ist ein integraler Teil des Prozesses – und unsere bisherige Erfahrung stützt das.

Wenn wir in KI-generiertem Code auf Probleme wie die zuvor aufgedeckten stoßen, haben wir zwei Optionen:
- Sie manuell beheben, vorausgesetzt, wir können alle Probleme selbst identifizieren
- Dieselbe KI verwenden, um den von ihr generierten Code zu verfeinern und zu korrigieren – ein völlig gültiger und oft effektiver Teil des Workflows

In der Praxis ist der Bau einer produktionsreifen App fast immer eine wiederholte Kombination beider Techniken.

In diesem Abschnitt iterieren wir ein paar Mal auf der App – Probleme aufzeigen, die Implementierung verfeinern und uns schrittweise auf ein vollständigeres und zuverlässigeres Ergebnis zubewegen.

### E1. KI verwenden, um Probleme zu identifizieren und zu beheben

1. Formulieren Sie am Genie-Code-Prompt eine Anfrage wie diese:

> Is this app production-ready?

> Auch das ist ein sehr einfacher Prompt, aber mehr als genug, um den Punkt zu veranschaulichen.

2. Genie Code macht sich an die Arbeit und überdenkt einige seiner früheren Entscheidungen. Bald kommt es zu derselben Schlussfolgerung, auf die wir hingearbeitet haben: **noch nicht**. Es schlägt Korrekturen für die Probleme vor, die wir bereits aufgezeigt haben, und einige, die wir nicht aufgezeigt haben. Nehmen wir die Option an, die kritischen Probleme zu beheben.
3. Sobald die Änderungen vorgenommen sind, werden wir aufgefordert, sie anzunehmen, genau wie bei der ersten App-Erstellung. Nehmen wir diese jetzt an, indem wir auf **Accept all** klicken.

### E2. Spezifische Probleme adressieren

Nach einem Durchgang zur Behebung kritischer Probleme adressieren wir nun das frühere Konfigurationsproblem. Erinnern Sie sich, dass der App-Code so geschrieben wurde, dass er einen HTTP-Pfad erwartet, während App-Ressourcen eine Warehouse-ID bereitstellen.

Verwenden wir jetzt KI, um das zu beheben.

1. Formulieren Sie am Genie-Code-Prompt eine Anfrage wie diese:

> Modify the app to accept the SQL warehouse ID rather than the HTTP path.

> Auch das ist ein sehr einfacher Prompt, aber mehr als genug, um den Punkt zu veranschaulichen.

2. Genie Code macht sich an die Arbeit und modifiziert letztlich den Code (`app.py`) und die YAML (`app.yaml`), um sich an eine Konvention zur Übergabe der Warehouse-ID anzupassen.

Das mag auf den ersten Blick kein großer Gewinn erscheinen, aber es macht die App-Konfiguration letztlich einfacher und im Einklang mit konventionellen Praktiken:
- ein SQL Warehouse als Ressource hinzufügen
- den Ressourcennamen in der YAML-Datei über `valueFrom` auf eine Umgebungsvariable abbilden
- Databricks stellt automatisch sicher, dass die Berechtigungen für die Nutzung des SQL Warehouse durch die App ausreichend sind

### E3. Die Korrekturen testen

> **Bei Verwendung des mitgelieferten Referenz-Quellcodes**

## F. Für bessere Ergebnisse prompten

In den vorherigen Abschnitten haben wir die KI-generierte Anwendung geprüft und mehrere Probleme identifiziert durch:
- Probleme, die während Setup und Konfiguration auftraten
- Beobachtung des Laufzeitverhaltens
- manuelle Inspektion des Codes
- KI-geprompteten Code-Review

Konzentrieren wir uns kurz auf den letzten Punkt. Interessanterweise erkannte das Modell, als wir es direkt fragten, ob der Code produktionsreif sei, schnell viele kritische Probleme und erklärte im Detail, warum sie wichtig waren. Was die Frage aufwirft:

> Wenn das Modell diese Probleme identifizieren kann, warum hat es sie nicht von vornherein vermieden?

Es liegt nicht daran, dass Genie Code, die von ihm genutzten LLMs oder KI-gestützte Entwicklung im Allgemeinen „schlecht" wären. Die Antwort liegt tatsächlich darin, wie Modelle Prompts interpretieren. Verbringen wir die letzten Minuten dieser Demo damit, diesen wichtigen Aspekt erfolgreichen Vibe Codings durchzugehen.

Aber bevor wir das tun, ist es wichtig zu erkennen, dass gutes Prompten von mehr abhängt als nur davon, zu beschreiben, was Sie bauen wollen. Es erfordert auch ein grundlegendes Verständnis dessen, was gute Software ausmacht – was zu validieren, was zu hinterfragen und was von einer robusten Implementierung zu erwarten ist. In diesem Licht kann Vibe Coding die Entwicklung hochwertiger Software erheblich beschleunigen – aber es ersetzt nicht das Engineering-Urteilsvermögen.

### F1. Die Kosten der Mehrdeutigkeit

Im Umgang mit jeder Form generativer KI ist das Schreiben klarer Prompts von entscheidender Bedeutung, und es ist auch eine Herausforderung. Prompts, die uns klar erscheinen, lassen aus Sicht eines Modells oft Details vermissen.

Wenn ein Prompt Raum für Interpretation lässt, muss das Modell die Lücken füllen. Dazu stützt es sich auf Muster aus seinen Trainingsdaten, vorherigen Kontext und statistische Wahrscheinlichkeiten, um zu entscheiden, was in dieser Situation Sinn ergibt. Manchmal stimmen diese Annahmen mit unserer Absicht überein. Manchmal nicht.

Jeder, der jemals Bildgenerierung versucht hat, kann das nachvollziehen.

**„The Catfish"** (Wortspiel: *catfish* = Wels; *to catfish someone* = jemanden mit falscher Identität täuschen)

> – Bitte generiere ein Bild eines Welses (catfish).
> – Erledigt!
> – Nein, ich meinte jemanden, der „gecatfisht" wird.
> – Ohhh! Aktualisiertes Bild.
> – Können wir ihn zu dem machen, der gecatfisht wird?
> – Absolut, hoffe es gefällt Ihnen!

**„Cat in a Hat"** (Katze in/mit Hut)

> – Bitte generiere ein Bild einer Katze mit Hut.
> – Bitte sehr.
> – Wels mit Hut?
> – Hast du's.
> – Wie wäre es mit einem Hasen im Hut?
> – Klar doch!

#### F1.1 Beispiele aus der Bildgenerierung

Ausgehend vom Beispiel *Cat in a hat* aus dem vorherigen Abschnitt: Auch wenn es für einen Menschen klar klingt, ist dieser Prompt für ein Modell unglaublich mehrdeutig. Bedenken Sie die Möglichkeiten, was „in" in diesem Kontext bedeuten könnte:

- Katze, die einen Hut trägt (am wahrscheinlichsten)
- Katze im Inneren eines Hutes
- Hut mit einer Katze darauf

In Ermangelung einer klaren Anweisung füllt das Modell die Lücke, indem es die wahrscheinlichste Option wählt.

Dieselbe Mehrdeutigkeit besteht, wenn man nach einem „Catfish in a hat" fragt. Obwohl ein Fisch, der von einem Hut umschlossen ist, plausibler erscheinen würde, könnte das Modell aufgrund räumlicher Beziehungen „tragend" gewählt haben, oder weil es vom Muster „a cat in a hat" beeinflusst wurde, das noch im Kontext ist.

Obwohl „Rabbit in a Hat" technisch immer noch dieselbe Mehrdeutigkeit hat, ist das Modell durch die Millionen von Bildern von „Hase im Hut"-Zaubertricks verankert, die es gesehen hat. Plötzlich erscheint die Behälter-Beziehung als klarer Gewinner, um die Lücke zu füllen:

- Hase im Inneren eines Hutes (am wahrscheinlichsten, mit Abstand)
- Hase, der einen Hut trägt
- Hut mit einem Hasen

Um diese Voreingenommenheit zu überschreiben, müssten Sie spezifischer prompten; zum Beispiel „Rabbit wearing a hat" (Hase, der einen Hut trägt).

#### F1.2 Beispiele aus der Code-Generierung

Genau dieses Phänomen gilt auch für Code, nur dass der Einsatz jetzt höher ist.
- Mehrdeutigkeit in Bildgenerierungs-Prompts → sofort sichtbar (Ergebnis passt nicht zur Absicht, seltsame Artefakte)
- Mehrdeutigkeit in Code-Generierungs-Prompts → plausibel aussehender Code mit Problemen, die nicht immer offensichtlich sind (Sicherheitslücken, schlechte Standardwerte, brüchige Logik, Race Conditions)

Der Prompt, den wir verwendet haben, scheint das Ziel der Anwendung und die gewünschte Funktionalität klar zu beschreiben. Aber er lässt auch viele wichtige Details unspezifiziert:

| Was unspezifiziert ist | Was das Modell entscheiden muss |
| --- | --- |
| Zu verwendende Tabelle | Spezifische Tabelle vs. vom Benutzer ausgewählt; wie die Tabelle identifiziert oder bereitgestellt wird |
| Was „bearbeiten" bedeutet | Inline- vs. formularbasierte Bearbeitung; vollständiger Zeilenersatz vs. partielle Updates |
| Validierungsregeln | Bearbeitbare Spalten, Pflichtfelder, Typbeschränkungen, NULL-Behandlung |
| Datenzugriffsmuster | Zugriffsmethode auf das SQL Warehouse; direkte Queries vs. Abstraktionsschicht |
| Fehlerbehandlung | Verhalten bei fehlgeschlagenen Updates, ungültiger Eingabe oder Query-Fehlern |
| Nebenläufigkeitsmanagement | Kollidierende Bearbeitungen von mehreren Benutzern; Überschreiben vs. Konfliktauflösung |
| UI-Framework | Streamlit, Flask, statisches HTML oder ein anderes Muster |
| Was „fertig" bedeutet | Demo- vs. Produktionserwartungen; Einschränkungen, Robustheit und Feinschliff |

Diese fehlenden Details bleiben nicht neutral; das Modell füllt sie aus. Und genau wie bei der Bildgenerierung stimmen diese Annahmen manchmal mit Ihrer Absicht überein und manchmal nicht. Schlimmer noch, manchmal führen sie zu fehlerhaftem oder buggy Code.

Der Schlüssel zu besseren Ergebnissen ist nicht, perfekte Ausgabe zu erwarten, sondern klarere Anleitung zu geben. Im nächsten Abschnitt zerlegen wir, was einen effektiven Prompt ausmacht und wie man Mehrdeutigkeit in der Praxis reduziert.

### F2. Anatomie eines effektiven Prompts

Die Qualität der Ausgabe von Genie Code ist direkt proportional zur Qualität des Eingabe-Prompts. Wie wir zuvor gesehen haben, füllt das Modell die Lücken mit Annahmen, wenn Schlüsseldetails unspezifiziert bleiben – manchmal korrekt und manchmal nicht.

Ein effektiver Prompt reduziert diese Mehrdeutigkeit, indem er die wichtigen Aspekte der Anwendung explizit beschreibt. Nicht jeder Prompt muss all diese Elemente enthalten, aber je klarer Sie sie definieren, desto vorhersehbarer und zuverlässiger wird die generierte Ausgabe.

| Element | Zweck | Beispiel |
| --- | --- | --- |
| **App-Zweck** | Definiert das übergeordnete Ziel der Anwendung | Eine App zum Ansehen und Bearbeiten von Daten in einer Unity-Catalog-Tabelle |
| **Datenquelle** | Verankert das Modell an realen Schema-Objekten | Erlaube dem Benutzer, eine Tabelle aus jedem erlaubten Catalog und Schema auszuwählen |
| **Datenbehandlung** | Sichert korrekte Interpretation und Verarbeitung von Datentypen und Semantik | Behandle Datentypen angemessen, nicht als Strings |
| **Schlüsselspalten** | Reduziert Halluzinationsrisiko und klärt die Schema-Nutzung | Erlaube Filtern und Sortieren auf String- und Datumsspalten |
| **Ausgabeformat** | Gibt an, wie Ergebnisse präsentiert werden sollen | Zeige die Tabelle in einem bearbeitbaren Grid mit Inline-Bearbeitungsunterstützung an |
| **Benutzerinteraktion** | Beschreibt erwartete Steuerelemente und Eingaben | Erlaube Benutzern, neue Zeilen hinzuzufügen, bestehende Zeilen inline zu bearbeiten und ausgewählte Zeilen zu löschen |
| **Einschränkungen** | Definiert Grenzen für Umfang, Layout oder Verhalten | Halte die App auf einer einzigen Seite mit einer einfachen Tabellenansicht und minimalem Styling |
| **Fehlerbehandlung** | Definiert, wie die App auf ungültige Eingaben oder Fehler reagieren soll | Zeige klare Fehlermeldungen bei ungültiger Eingabe an und verhindere die Übermittlung fehlerhafter Daten |
| **Qualitätserwartungen** | Setzt Erwartungen an Robustheit, Korrektheit und Produktionsreife | Generiere sauberen, modularen Code mit Eingabevalidierung, Fehlerbehandlung und klarer Trennung zwischen UI- und Datenzugriffslogik |

Jedes dieser Elemente reduziert die Notwendigkeit für das Modell, Annahmen zu treffen. Je präziser Sie sie definieren, desto mehr Kontrolle behalten Sie über das generierte Ergebnis.

### F3. Schwache und starke Prompts vergleichen

Die folgenden Beispiele veranschaulichen, wie die Prompt-Qualität die Ausgabequalität beeinflusst.

**Schwacher Prompt:**

> Please write an app that allows me to view a UC table and edit, add and delete rows. Write the app source in a folder named "vibe_app" in my user home folder. Do not actually create the app; I will deploy the source to an existing app.

Das erscheint uns anständig, aber wie wir gesehen haben, gibt das Genie Code wenig bis keine Informationen über tatsächliche Implementierungsdetails. Daraus füllt es viele Lücken mit Annahmen und baut das absolute Minimum, um dieses Ziel zu erfüllen.

**Stärkerer Prompt:**

> Please write a simple single-page Databricks app that allows a user to view and edit data in a Unity Catalog table.
>
> Allow the user to:
> - select a catalog, schema, and table
> - view the contents of the selected table
> - add, edit, and delete rows
>
> Use the table schema to determine column names and data types. Handle all data types appropriately when converting between SQL and Python.
>
> Keep the layout simple and easy to use, and show clear error messages if an operation fails.
>
> Write production-quality code, avoiding shortcuts and unsafe operations that might violate trust boundaries.
>
> Write the app source code in a folder named "vibe_app_improved" in my user home folder. Do not deploy the app; I will handle that separately.

Dieser verbesserte Prompt ändert das Ziel der Anwendung nicht dramatisch. Er entfernt lediglich einige der wichtigen Annahmen und gibt dem Modell weit weniger Raum, falsch zu raten.

Das ist kein perfekter Prompt … aber er ist besser.

Wenn die Zeit es erlaubt, probieren Sie den verbesserten Prompt aus und vergleichen Sie die Ergebnisse mit zuvor.

### F4. Strategie der iterativen Prompt-Verfeinerung

Selbst mit einem stärkeren Prompt ist das erste Ergebnis immer noch ein Entwurf. Das Ziel ist nicht, Iteration zu eliminieren, sondern jede Iteration fokussierter und produktiver zu machen.

**Was passierte, als wir den Prompt verbesserten?**

Der überarbeitete Prompt erzeugte einen merklich besseren Ausgangspunkt – führte aber auch neue Annahmen und Probleme ein.

**Was sich verbesserte:**
- Reichhaltigere UI mit Catalog-, Schema- und Tabellenauswahl
- Bessere Nutzung von Schema-Informationen und Datentypen
- Strukturierteres und realistischeres Anwendungs-Scaffold
- Korrekte Validierung und Behandlung von SQL-Bezeichnern und -Parametern

**Was zu prüfen ist:**
- Unerwartete Framework-Wahl (`gradio`)
- Automatische Auswahl eines SQL Warehouse im Code, was bequem ist, aber nicht mit den Praktiken der App-Ressourcen-Bereitstellung übereinstimmt
- Falsch konfigurierte Gradio-Einstellungen in `app.yaml`
- Laufzeitfehler beim Laden, der weitere Untersuchung erfordert

Das ist zu erwarten. Ein stärkerer Prompt reduziert Mehrdeutigkeit, aber er eliminiert sie nicht. Das Modell füllt weiterhin Lücken – nur weniger, und oft mit vernünftigeren.

Hier wird iterative Verfeinerung entscheidend. Statt zu versuchen, jedes Detail im Voraus zu antizipieren, verfeinern wir den Prompt basierend auf dem, was wir beobachten.

Verwenden Sie die folgende Strategie, um effektiv zu iterieren:

1. **Breit starten, dann eingrenzen** – zuerst eine funktionierende App bekommen, dann spezifische Komponenten verfeinern
2. **Eine Änderung pro Prompt** – jede Modifikation isolieren, um Ergebnisse leichter bewerten zu können
3. **Auf den generierten Code verweisen** – bei Änderungsanfragen spezifische Funktionen, Variablen oder Komponenten zitieren
4. **Bestätigen vor dem Fortfahren** – die App nach jeder Iteration ausführen und prüfen
5. **Funktionierende Zustände speichern** – die Versionshistorie verwenden, um vor bedeutenden Änderungen einen Checkpoint zu setzen

Dieser Ansatz hält die Feedback-Schleife eng und verhindert, dass sich kleine Probleme zu größeren aufsummieren.

## H. Fazit

Diese Demo hat den vollständigen Vibe-Coding-Workflow durchgearbeitet – vom initialen Prompt über generierten Code bis zu Review, Iteration und Verfeinerung.

Wichtigste Erkenntnisse:

1. **Vibe Coding ermöglicht schnelles Prototyping** – eine Beschreibung in einfacher Sprache kann in Minuten ein lauffähiges App-Scaffold produzieren.
2. **KI-generierter Code muss geprüft werden** – falsche Annahmen, fragile Logik und fehlende Sicherungen sind die Norm, nicht die Ausnahme.
3. **Iteration ist die Kernfähigkeit** – die Fähigkeit, Probleme zu identifizieren und Prompts zu verfeinern, ist wertvoller als das Schreiben eines perfekten ersten Prompts.
4. **Prompt-Qualität formt Ergebnisse** – je klarer Sie Daten, Verhalten und Einschränkungen definieren, desto vorhersehbarer das Ergebnis.

Letztlich geht es bei Vibe Coding nicht darum, Engineering-Urteilsvermögen zu ersetzen – es geht darum, die Entwicklung zu beschleunigen und dabei die Kontrolle zu behalten.

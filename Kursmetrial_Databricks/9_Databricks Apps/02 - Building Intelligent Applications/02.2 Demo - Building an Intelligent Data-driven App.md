# Demo – Eine intelligente datengetriebene App erstellen

Databricks Apps machen es möglich, interaktive operative Anwendungen direkt auf der Databricks-Plattform zu erstellen – sie verbinden verwaltete Daten, Backend-APIs, benutzerdefinierte Oberflächen und KI-gestützte Workflows, ohne dass eine separate Infrastruktur oder Deployment-Plattform erforderlich ist.

In dieser Demo erstellen und deployen wir eine schlanke Anwendung für den Versorgungsbetrieb, die fiktive Standorte der Stromverteilung mithilfe verwalteter Unity-Catalog-Daten überwacht. Die App kombiniert Betriebskennzahlen, Störungen, Wartungsaktivitäten und KI-generierte operative Briefings zu einem einzigen workflow-orientierten Erlebnis.

Dabei erkunden wir mehrere zentrale Muster der Anwendungsentwicklung für Databricks Apps, darunter das Verbinden mit Databricks SQL Warehouses, das Konfigurieren von App-Ressourcen, das Bereitstellen von Backend-API-Routen, die Integration mit Model-Serving-Endpunkten und das Durchsetzen von verwaltetem Zugriff über Unity-Catalog-Berechtigungen. Wir betrachten außerdem, wie kuratierte Views die Anwendungsentwicklung vereinfachen können, indem sie stabile, anwendungsfertige Datenverträge bereitstellen.

Statt sich auf Frontend-Frameworks oder UI-Komplexität zu konzentrieren, betont diese Demo praktische Architekturmuster, die sich über ein breites Spektrum von Enterprise-Anwendungen wiederverwenden lassen – besonders solche, die verwaltete operative Daten mit KI-gestützter Entscheidungsunterstützung kombinieren.

## B. Eine datengetriebene App erkunden

Die App, die wir in dieser Demo erkunden, implementiert eine schlanke Anwendung für den Versorgungsbetrieb, die eingehende Daten von Standorten der Stromverteilung überwacht. Das Szenario ist fiktiv, aber diese Art von Anwendung ist nützlich, wenn Teams mehr als ein Dashboard brauchen: Sie brauchen einen interaktiven Workflow, der verwaltete Daten, operativen Kontext und KI-gestützte Interpretation zusammenbringt.

Obwohl bemerkenswert einfach, erlaubt diese Implementierung Benutzern, Versorgungsstandorte zu prüfen, aktuelle Betriebskennzahlen zu inspizieren, zugehörige Störungen und Wartungsaktivitäten anzusehen und ein operatives KI-Briefing für einen ausgewählten Standort zu generieren, das Fragen beantwortet wie:

#### B3.2 Logging-Konfiguration

Dieser Abschnitt ist für das Herstellen eines Handles zum Logger verantwortlich.

**app.py**

```python
import os
import sys
import logging
from databricks import sql
from databricks.sdk.core import Config
from flask import Flask, jsonify, render_template

DATABRICKS_APP_NAME = os.environ.get("DATABRICKS_APP_NAME", "grid-app")
DATABRICKS_WAREHOUSE_ID = os.environ.get("DATABRICKS_WAREHOUSE_ID", "")
SITE_OVERVIEW_VIEW = os.environ.get("SITE_OVERVIEW_VIEW", "")
SITE_INCIDENT_DETAIL_VIEW = os.environ.get("SITE_INCIDENT_DETAIL_VIEW", "")
SITE_MAINTENANCE_DETAIL_VIEW = os.environ.get("SITE_MAINTENANCE_DETAIL_VIEW", "")

app = Flask(__name__)
cfg = Config()

logger = logging.getLogger(DATABRICKS_APP_NAME)
logger.setLevel(logging.INFO)
logger.propagate = False

if not logger.handlers:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(
        logging.Formatter("[%(asctime)s] [%(name)s] [%(levelname)s] %(message)s")
    )
    logger.addHandler(handler)
```

- **Importe** (Zeilen 2–3): Das Modul `logging` stellt die Python-Logger-Funktionalität bereit, während `sys` die Definition von `stdout` liefert.
- **Logger einrichten** (Zeilen 17–19): Richtet das Logger-Objekt gemäß dem aus `DATABRICKS_APP_NAME` bezogenen App-Namen ein. Bei Bedarf könnte die minimale Schwere über eine Umgebungsvariable konfiguriert werden; es gibt jedoch kaum einen Nachteil, auch Info-Meldungen zusätzlich zu allem Schwerwiegenderen zu erfassen.
- **Stream-Handler einrichten** (Zeilen 21–26): Fügt einen Stream-Handler hinzu, der Log-Meldungen nach `stdout` schreibt, damit sie im Tab **Logs** von Databricks Apps erscheinen. Die Prüfung `if not logger.handlers` ist wichtig, um den Handler nicht mehrfach anzuhängen, falls dieser Code mehr als einmal ausgeführt wird – das würde zu doppelten Log-Meldungen führen. Hier könnten weitere Handler ergänzt werden, wenn Sie die Meldungen anderswo speichern möchten (z. B. in einer persistenten Datenbank).

#### B3.3 Databricks-Konnektivität und Abfragen

Dieser kleine Codeabschnitt liefert den „Klebstoff", der benötigt wird, um über das SQL Warehouse auf in Unity Catalog gespeicherte tabellarische Daten zuzugreifen.

**app.py**

```python
def get_connection():
    return sql.connect(
        server_hostname=cfg.host,
        http_path=f"/sql/1.0/warehouses/{DATABRICKS_WAREHOUSE_ID}",
        credentials_provider=lambda: cfg.authenticate
    )

def query_all(statement: str, params: tuple = ()):
    def rows_to_dicts(cursor):
        columns = [desc[0] for desc in cursor.description]
        return [dict(zip(columns, row)) for row in cursor.fetchall()]

    with get_connection() as conn:
        with conn.cursor() as cursor:
            cursor.execute(statement, params)
            return rows_to_dicts(cursor)
```

- **Mit SQL Warehouse verbinden** (Zeilen 1–6): Verbindet sich mit dem SQL Warehouse über den Databricks-SQL-Connector ([AWS](https://docs.databricks.com/aws/en/dev-tools/python-sql-connector) | [Azure](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/python-sql-connector) | [GCP](https://docs.databricks.com/gcp/en/dev-tools/python-sql-connector)). Hier werden `server_hostname` und `credentials_provider` vom zuvor instanziierten `Config`-Objekt bereitgestellt, während `http_path` mithilfe des aus `DATABRICKS_WAREHOUSE_ID` bezogenen Werts abgeleitet wird.
- **Query ausführen** (Zeilen 8–16): Führt ein SQL-Statement mit der Methode `cursor.execute()` aus. Die verschachtelte Funktion `rows_to_dicts()` entpackt alle von der Query zurückgegebenen Daten in eine Python-Dictionary-Struktur.

#### B3.4 API-Routen

Dieser Codeabschnitt beginnt die Implementierung der verschiedenen von diesem Backend unterstützten API-Endpunkte, darunter:

* `GET /` – Stellt die Frontend-Anwendung bereit, einschließlich des HTML, CSS und JavaScript, das zum Rendern der Dashboard-UI verwendet wird.
* `GET /api/sites` – Gibt die Liste der überwachten Versorgungsstandorte und ihren aktuellen operativen Zustand zurück.
* `GET /api/summary` – Gibt aggregierte operative Statistiken zurück, die zum Befüllen der Zusammenfassungs-Karten des Dashboards verwendet werden.
* `GET /api/sites/<site_id>` – Gibt detaillierte operative Informationen für einen einzelnen Versorgungsstandort zurück.
* `GET /api/sites/<site_id>/details` – Gibt ein konsolidiertes operatives Detail-Bündel für einen Standort zurück.

**app.py**

```python
@app.route("/")
def index():
    return render_template("index.html")

@app.route("/api/sites")
def get_sites():
    logger.info("site list requested")

    rows = query_all(f"""
        SELECT site_id, site_name, region, site_type,
          city, state_province, capacity_mw, criticality,
          measured_at, load_mw, load_pct, voltage_kv,
          temperature_c, health_score, status, active_incidents, next_maintenance
        FROM {SITE_OVERVIEW_VIEW}
        ORDER BY
          CASE status
            WHEN 'Critical' THEN 1
            WHEN 'Warning' THEN 2
            WHEN 'Elevated' THEN 3
            ELSE 4
          END,
          load_pct DESC
    """)

    return jsonify(rows)
```

- **Frontend-Bereitstellung** (Zeilen 1–3): Wenn ein Benutzer die Basis-URL der App (`/`) aufruft, wird diese Route aufgerufen, die die Frontend-UI rendert (enthalten in `templates/index.html`).
- **API-Endpunkt /api/sites** (Zeilen 5–6): Stellt den API-Endpunkt bereit, der die Liste der überwachten Versorgungsstandorte und ihren aktuellen operativen Zustand zurückgibt.
- **Anfrage protokollieren** (Zeile 7): Ausführliches Logging mit passenden Schwere-Levels ist eine hervorragende Praxis und kann für App-Profiling und Debugging sehr hilfreich sein.
- **Query ausführen** (Zeilen 9–23): Führt ein `SELECT`-Statement aus, um Standorte und operative Informationen zu sammeln, sortiert nach Kritikalität. Es verwendet die zuvor besprochene Funktion `query_all()`, die die Query auf dem konfigurierten SQL Warehouse ausführt.
- **JSON-Dokument zurückgeben** (Zeile 25): Konvertiert und gibt die Ergebnisse im erwarteten JSON-Format zurück.

Die übrigen Endpunkte folgen einem ähnlichen Muster, daher gehen wir sie nicht alle durch.

### C1. Das SQL Warehouse identifizieren

Im Kontext einer App auf Enterprise-Niveau wäre es wünschenswert, Apps, die eines benötigen, ein dediziertes SQL Warehouse zuzuweisen. In einem allgemeineren Demo-Kontext kann die Nutzung eines beliebigen SQL Warehouse jedoch ausreichen, solange es eine der folgenden Bedingungen erfüllt:
- Der App-Ersteller hat `IS_OWNER` oder `CAN_MANAGE` auf dem SQL Warehouse, was das Erteilen von `CAN_USE` an den App-Service-Principal ermöglicht
- Das Warehouse erteilt bereits `CAN_USE` an alle Workspace-Benutzer, in welchem Fall keine zusätzlichen Berechtigungen erforderlich sind

Wir empfehlen außerdem die Verwendung eines Warehouse, das:
- wahrscheinlich nicht gelöscht wird, da das die App-Funktionalität ernsthaft beeinträchtigen würde
- Serverless Compute verwendet, um lange Verzögerungen zu vermeiden, falls das Warehouse für eine App-Anfrage neu gestartet werden muss

Identifizieren Sie im [Tab SQL Warehouses](/compute/sql-warehouses) ein Warehouse, das diese Kriterien erfüllt, und notieren Sie es.

Dieser Ansatz kann effizienter skalieren, aber das hier verwendete Muster „eine Ressource pro View" veranschaulicht besser, wie Databricks-Apps-Ressourcen mit Unity-Catalog-Governance und Anwendungskonfiguration integriert sind.

### C4. Die Auswirkungen des Ressourcen-Hinzufügens erkunden

Kehren Sie zum Datensatz-Schema im Catalog Explorer zurück, um die Berechtigungen zu inspizieren, die automatisch angewendet wurden, als die Ressourcen zur App hinzugefügt wurden.

Beispielsweise sehen Sie im Tab **Permissions** der View `site_overview`, dass der **Service Principal** der App nun das Privileg **`SELECT`** hat.

Ähnliche Berechtigungen wurden auch auf die anderen konfigurierten Tabellen angewendet. Zusätzlich haben das enthaltende Schema und der Catalog die erforderlichen Traversal-Berechtigungen, die notwendig sind, damit die Anwendung erfolgreich auf diese Ressourcen zugreifen kann.

Dieses Berechtigungsmanagement-Verhalten ist eine Bequemlichkeit, die beim Hinzufügen von UC-Tabellen-Ressourcen zu einer Databricks App bereitgestellt wird, und erspart Ihnen die manuelle Konfiguration dieser Berechtigungen.

> **Wichtiger Hinweis**

> Automatische Berechtigungserteilungen funktionieren nur, wenn der App-Ersteller die zugehörigen Views/Tabellen sowie das enthaltende Schema und den Catalog besitzt (oder das Privileg `CAN MANAGE` darauf hat).

## E. Die App mit KI erweitern

In diesem Abschnitt erweitern wir die App von einer rein datengetriebenen operativen Anwendung zu einer intelligenten datengetriebenen Anwendung, indem wir KI-generierte operative Briefings mit einem LLM hinzufügen. Diese Briefings gehen über die bloße Präsentation roher operativer Daten hinaus, indem sie Schlussfolgerungen basierend auf Störungen, Wartungsaktivität und dem gesamten operativen Kontext ziehen und so helfen, rohe Daten in umsetzbare Erkenntnisse zu verwandeln.

Um der Anwendung Zugriff auf ein LLM zu geben, ist der einfachste Startpunkt bei von Databricks gehosteten Foundation Models, die über Databricks Model Serving bereitgestellt werden. Das sind vorgehostete, produktionsreife Modelle, die über Foundation Model APIs verfügbar gemacht werden und Teams erlauben, Fähigkeiten wie Zusammenfassung, operative Analyse und Generierung von Action Items hinzuzufügen, ohne ihre eigene Modell-Infrastruktur deployen oder verwalten zu müssen.

Model Serving bietet einen einheitlichen Mechanismus zum Deployen und Abfragen von Modellen. Speziell für Foundation Models stellt Databricks eine OpenAI-kompatible API und ein SDK bereit, was die Integration aus Anwendungscode erheblich vereinfacht. Innerhalb der App selbst ist das Implementierungsmuster unkompliziert:

- den Serving Endpoint als App-Ressource deklarieren
- dem App-Service-Principal `CAN_QUERY` erteilen
- den Endpunkt vom Backend mit dem Databricks SDK aufrufen

### E1. Strukturelle Aktualisierungen

Um die neue KI-Funktionalität einzubauen, ist die Gesamtauswirkung auf die Anwendungsstruktur relativ gering. Hauptsächlich umfasst die Erweiterung:
- Discovery des Model-Serving-Endpunkts
- Hinzufügen einer neuen Backend-Route, die einen operativen Prompt über den Model-Serving-Endpunkt an ein LLM sendet
- eine kleine Anzahl zusätzlicher UI-Elemente im Frontend, um den neuen API-Endpunkt auszulösen und das resultierende operative Briefing innerhalb des bestehenden Anwendungs-Workflows zu rendern

### E2. Backend-Aktualisierungen

#### E2.2 Databricks-Konnektivität und Abfragen

Dieser kleine Codeabschnitt bietet Zugriff auf LLM-Fähigkeiten über einen Model-Serving-Endpunkt.

**app.py**

```python
def query_llm(
    prompt: str,
    temperature: float = 0.0,
    system_prompt: str = """
You are an operations analyst for an electrical distribution company.
Your job is to help operators quickly identify what matters.
Do not repeat raw data unless it supports a risk, anomaly, or recommendation.
Be concise, practical, and action-oriented.
""",    
    max_tokens: int = 1024,
):
    response = w.serving_endpoints.query(
        name=ENDPOINT_NAME,
        messages=[
            ChatMessage(
                role=ChatMessageRole.SYSTEM,
                content=system_prompt,
            ),
            ChatMessage(
                role=ChatMessageRole.USER,
                content=prompt,
            ),
        ],
        # temperature=temperature,
        max_tokens=max_tokens,
    )

    if response.choices and len(response.choices) > 0:
        return response.choices[0].message.content

    return None
```

- **LLM-Query-Funktion** (Zeile 1): Diese einfache Funktion sendet einen Prompt an das LLM und gibt die Antwort zurück.
- **System-Prompt** (Zeilen 5–8): Der System-Prompt liefert grundlegende Verhaltens- und Generierungsvorgaben, die automatisch auf alle über diese Funktion gesendeten Queries angewendet werden.
- **Maximale Ausgabe-Token** (Zeile 10): Der Parameter `max_tokens` begrenzt die maximale Anzahl von Token, die das LLM ausgibt. Beachten Sie, dass die Definition eines Tokens modellspezifisch ist und typischerweise nicht einem Wort entspricht. Größere Werte können die Antwortlatenz und -kosten erhöhen, während aggressiv niedrige Werte zu abgeschnittener Ausgabe führen können.
- **Die Query senden** (Zeilen 12–26): Strukturiert und sendet die Nachricht an den Model-Serving-Endpunkt.
- **Antwort extrahieren** (Zeilen 28–29): Extrahiert und gibt den Text aus der Antwortstruktur zurück.

#### E2.3 API-Routen

Eine Route wird der App hinzugefügt, um die neue Funktionalität zu unterstützen:

* `POST /api/sites/<site_id>/briefing` – Generiert ein konsolidiertes operatives Detail-Bündel für einen Standort.

**app.py**

```python
@app.post("/api/sites/<site_id>/briefing")
def get_site_briefing(site_id):
    logger.info("site briefing requested site_id=%s", site_id)

    if not ENDPOINT_NAME:
        logger.warning("briefing rejected: ENDPOINT_NAME not configured")
        return jsonify({"error": "Model serving endpoint is not configured."}), 500

    details = fetch_site_details(site_id)

    if not details:
        return jsonify({"error": "Site not found"}), 404

    prompt = f"""
Use the JSON payload below to produce a compact operational briefing for a narrow application side panel.

Do NOT simply restate every field. Focus only on what matters, why it matters, and what the operator should do next. Write in this exact format:

Assessment: One sentence, maximum 25 words.
Key concerns: maximum 3 bullets, 15 words each.
Recommended actions: maximum 3 bullets, 15 words each.

Rules:
- Use only the JSON payload.
- Do not invent facts.
- Avoid markdown tables.
- Avoid headings other than the exact labels above.

JSON payload:
{json.dumps(details, default=str, indent=2)}
"""

    try:
        briefing = query_llm(prompt)
    except Exception as e:
        logger.error("briefing generation failed site_id=%s error=%r", site_id, e)
        return jsonify({"error": "Could not generate operational briefing."}), 500

    return jsonify({
        "briefing": briefing,
    })
```

- **Neue Route** (Zeile 1): Diese Route ist eine Neuerung. Beachten Sie, dass dieser Endpunkt `POST` erfordert. Wir denken zwar an diese Route als eine, die Informationen abruft, aber `POST` ist hier passender, weil etwas Neues generiert wird. Diese Generierung löst KI-Inferenz-Arbeit im Backend aus, statt einfach eine statische Ressource abzurufen.
- **Standortdetails abrufen** (Zeile 9): Diese Hilfsfunktion (auch von anderen API-Routen verwendet) sammelt eine strukturierte Darstellung aller Details, die sie zum betreffenden Standort finden kann.
- **Prompt** (Zeilen 15–30): Wie bei allem rund um generative KI liefern bessere Prompts bessere Ergebnisse. Hier sehen wir einen sehr strukturierten Prompt, der klare Vorgaben zum Thema und zur Strukturierung der Antwort macht. Eine JSON-Nutzlast mit den abgerufenen Daten wird ebenfalls in den Kontext aufgenommen, um dem LLM zu helfen, eine Antwort zu formulieren, die für die aktuelle Situation am angegebenen Standort relevant ist.
- **Query ausführen** (Zeile 34): Sendet die Query über die zuvor besprochene Funktion `query_llm()`, die die Query auf dem konfigurierten Model-Serving-Endpunkt ausführt.
- **JSON-Dokument zurückgeben** (Zeilen 39–41): Konvertiert und gibt die Ergebnisse im erwarteten JSON-Format zurück.

Die übrigen Endpunkte folgen einem ähnlichen Muster, daher gehen wir sie nicht alle durch.

### E4. Eine Model-Serving-Endpunkt-Ressource hinzufügen

Databricks Model Serving bietet Optionen bei der Entscheidung, welches LLM-Modell Sie in Ihrer App verwenden möchten. Databricks unterstützt sowohl von Databricks gehostete Foundation Models als auch extern gehostete Anbieter wie OpenAI und Anthropic hinter einer konsistenten Serving-Erfahrung. Das erlaubt Teams, Modelle basierend auf den Anforderungen der Workload und der Anwendungserfahrung auszuwählen.

Für ein operatives Dashboard wie dieses umfasst die Modellauswahl typischerweise praktische Kompromisse, darunter:

* Zusammenfassungsqualität
* Antwortlatenz
* Serving-Kosten
* regionale Verfügbarkeit
* Durchsatz- und Nebenläufigkeitsanforderungen
* Preismodell (Pay-per-Token versus Provisioned Throughput)

Während der Entwicklung dieser Demo etwa beeinflussten verschiedene Modelle merklich nicht nur die Qualität der generierten operativen Briefings, sondern auch ihre Ausführlichkeit, Reaktionsfähigkeit und das Gesamterlebnis innerhalb der Anwendung.

Prüfen Sie die verfügbaren Optionen auf der Seite [Serving Endpoints](/ml/endpoints) und identifizieren Sie einen, den Sie mit der App ausprobieren, wie folgt:

1. Öffnen Sie den Tab **Settings** Ihrer App.
1. Klicken Sie im Bereich **Resources** auf **Add resource**.
1. Wählen Sie im Menü **Serving endpoint** und geben Sie die Optionen wie folgt an:
   - Wählen Sie einen der verfügbaren Endpunkte, etwa **databricks-gpt-5-4**
   - Geben Sie die Berechtigung **Can query** an.
   - Stellen Sie sicher, dass **Resource key** auf `serving-endpoint` gesetzt ist.
1. Klicken Sie auf **Save**.

## 1. Structured Streaming & Real-Time Processing

### 1.1 Real-Time Mode (Spark 4.x, 2025-2026)

[Ultra-Fast Anomaly Detection using Apache Spark Real-Time Mode](https://www.databricks.com/blog/ultra-fast-anomaly-detection-using-apache-spark-real-time-mode) — 2026-07-13
   - **Themen:** Apache Spark Real-Time Mode, operative Guardrail-Pipeline, Kafka-Integration, kontinuierlicher Datenfluss und Streaming Shuffle, Millisekunden-Latenz statt Mikrobatch
   - **Zusammenfassung:** Für Anwendungsfälle wie Betrugs- oder Anomalieerkennung reicht die klassische Mikrobatch-Verarbeitung von Spark mit ein bis zwei Sekunden Verzögerung oft nicht aus, weshalb Teams bislang häufig auf separate Engines wie Apache Flink auswichen. Der Artikel zeigt anhand einer Guardrail-Pipeline, die eingehende Ereignisse validiert und in Echtzeit als unbedenklich oder verdächtig einstuft, wie der neue Real-Time-Mode von Spark Structured Streaming dies direkt in der bestehenden Spark-API ermöglicht. Durch kontinuierlichen Datenfluss, parallele Verarbeitungsstufen und speicherbasiertes Shuffling wird eine sehr geringe Latenz erreicht, wobei die Umstellung im Wesentlichen über eine einzige Konfigurationsänderung erfolgt. Im beschriebenen Test mit rund 23 Millionen Ereignissen wurden P95-Latenzen unter einer halben Millisekunde erzielt, was zeigt, dass analytische und operative Streaming-Anforderungen künftig auf einer Plattform abgebildet werden können.

[Apache Spark Real-Time Mode for Gaming: A Better Way to Do Real-Time Sessionization](https://www.databricks.com/blog/apache-spark-real-time-mode-gaming-better-way-do-real-time-sessionization) — 2026-06-03
   - **Themen:** transformWithState Operator, MapState mit TTL, Timer-basierte Verarbeitung (handleExpiredTimer), Kafka-basierte Sessionization, Real-Time Mode für Gaming
   - **Zusammenfassung:** Gaming-Plattformen müssen Millionen gleichzeitiger Spielsitzungen mit sehr geringer Verzögerung verfolgen, um Personalisierung und Empfehlungen zu ermöglichen, wofür bisher oft separate Streaming-Engines wie Flink nötig waren. Der Artikel zeigt, wie der Real-Time-Mode von Spark zusammen mit dem Operator transformWithState sowohl ereignisgetriebene als auch timer-gesteuerte Logik in einer einzigen Engine vereint. Über einen Zustand je Sitzung und wiederkehrende Timer, etwa alle 30 Sekunden, lassen sich reaktive Ereignisse und proaktive Signale erzeugen, selbst wenn keine neuen Eingabedaten eintreffen. In den vorgestellten Messungen wurde eine p99-Latenz von rund 432 Millisekunden erreicht, etwa 20-mal schneller als im klassischen Mikrobatch-Modus, was zeigt, dass Spark hier mit spezialisierten Streaming-Systemen mithalten kann.

[How MakeMyTrip achieved millisecond personalization at scale with Databricks](https://www.databricks.com/blog/how-makemytrip-achieved-millisecond-personalization-scale-databricks) — 2026-04-07
   - **Themen:** Real-Time Mode / RealTimeTrigger, Aerospike-basierte Zustandsanreicherung, Redis-Caching, Kafka-Partitions-Multiplexing, Checkpoint- und Backpressure-Tuning
   - **Zusammenfassung:** MakeMyTrip benötigte für personalisierte Hotelempfehlungen Antwortzeiten im Millisekundenbereich, während die klassische Mikrobatch-Verarbeitung von Spark ein bis zwei Sekunden Verzögerung mit sich brachte. Die Lösung bestand darin, mit dem Real-Time-Mode von Spark Structured Streaming eine einzige Pipeline aufzubauen, die Klickstromdaten aus verschiedenen Kanälen zusammenführt, den Zustand über eine schnelle Schlüssel-Wert-Datenbank anreichert und die Ergebnisse über einen Cache ausliefert. Durch Anpassungen wie die Aufteilung der Kafka-Partitionen auf mehrere parallele Aufgaben sowie gezieltes Checkpoint- und Backpressure-Tuning konnte die vorher getrennte Zwei-Engine-Architektur zu einer einzigen vereinheitlicht werden. Damit sank die mittlere Latenz von gut einer Sekunde auf rund 44 Millisekunden, und die Klickrate stieg messbar an.

[Announcing General Availability of Real-Time Mode for Apache Spark Structured Streaming on Databricks](https://www.databricks.com/blog/announcing-general-availability-real-time-mode-apache-spark-structured-streaming-databricks) — 2026-03-19
   - **Themen:** Real-Time Mode (GA), transformWithState mit Initial State, Real-Time Trigger, Databricks Runtime 16.4, Vergleich zu Apache Flink
   - **Zusammenfassung:** Bislang mussten Unternehmen für sehr niedrige Latenzanforderungen neben Spark zusätzlich spezialisierte Systeme wie Flink betreiben, was zu doppeltem Code und höherem Betriebsaufwand führte. Mit der allgemeinen Verfügbarkeit des Real-Time-Mode stellt Databricks eine Erweiterung von Spark Structured Streaming vor, die durch kontinuierlichen Datenfluss, parallele Stufenausführung und speicherbasiertes Shuffling Latenzen im Millisekundenbereich direkt in der gewohnten Spark-API ermöglicht. Aktiviert wird der Modus über eine einfache Konfigurationsänderung, zusätzlich wurde der Zustandsoperator transformWithState um das Laden eines Ausgangszustands erweitert. In Benchmarks und bei Kunden wie Coinbase und MakeMyTrip zeigte sich eine deutlich geringere Latenz als bei Flink sowie ein einheitlicher Code für Batch-Training und Echtzeit-Inferenz.

[Breaking the microbatch barrier: The architecture of Apache Spark Real-Time Mode](https://www.databricks.com/blog/breaking-microbatch-barrier-architecture-apache-spark-real-time-mode) — 2026-03-16
   - **Themen:** Extended Epochs / Continuous Flow, nebenläufige Shuffle-Verarbeitung, nicht-blockierende Aggregations-Operatoren, Spark 4.1 Architektur, Real-Time Mode Interna
   - **Zusammenfassung:** Streaming-Systeme zwangen Anwender bisher dazu, sich zwischen hohem Durchsatz mit Spark oder niedriger Latenz mit spezialisierten Systemen wie Flink zu entscheiden, da eine reine Verkleinerung der Batchgröße wegen fixer Verarbeitungskosten wie Checkpointing keine echte Lösung war. Der Artikel erläutert die technische Architektur hinter dem Real-Time-Mode in Spark 4.1, bei der Daten innerhalb länger laufender Verarbeitungsabschnitte kontinuierlich fließen, nachgelagerte Stufen bereits mit der Verarbeitung beginnen können, sobald erste Zwischenergebnisse vorliegen, und Operatoren wie Gruppierungen so umgebaut wurden, dass sie Ergebnisse laufend statt gepuffert ausgeben. Dadurch lassen sich Latenzen im niedrigen zweistelligen Millisekundenbereich erreichen, wie sie etwa für Betrugserkennung nötig sind. Das Ergebnis ist eine einzige Engine, die sowohl klassische Batch-ETL- als auch Echtzeit-Anwendungsfälle abdeckt.

[Real-Time Mode: Ultra-low latency streaming on Spark APIs without a second engine](https://www.databricks.com/blog/real-time-mode-ultra-low-latency-streaming-spark-apis-without-second-engine) — 2026-03-02
   - **Themen:** Real-Time Mode Public Preview, RealTimeTrigger API, Vergleich zu AvailableNow-Trigger, kontinuierlicher Datenfluss und Pipeline-Scheduling, Benchmark gegen Apache Flink
   - **Zusammenfassung:** Weil separate Systeme für hohen Durchsatz und niedrige Latenz bislang doppelte Codebasen, getrennte Governance-Modelle und spezialisiertes Personal erforderten, beschreibt der Artikel die im August 2025 als Public Preview vorgestellte Real-Time-Mode-Funktion für Spark Structured Streaming. Durch kontinuierliche Datenverarbeitung, parallele Ausführung von Verarbeitungsstufen und direktes Shuffling ohne Zwischenspeicherung auf Platte wird eine deutlich geringere Latenz erreicht als im klassischen Trigger-Modus. Aktiviert wird der Modus über eine einfache Trigger-Konfiguration in der Spark-API, im Unterschied zum eher batch-artigen AvailableNow-Trigger. In Benchmarks erzielte der Ansatz bei Aufgaben wie Feature-Berechnung und Datenanreicherung eine deutlich geringere Latenz als Apache Flink und eignet sich damit für Anwendungen wie Betrugserkennung, Personalisierung und IoT-Überwachung.

### 1.2 Stateful Processing, transformWithState und State Store

[Announcing On-Demand State Repartitioning for Apache Spark™ Structured Streaming on Databricks](https://www.databricks.com/blog/announcing-demand-state-repartitioning-apache-sparktm-structured-streaming-databricks) — 2026-09-14
   - **Themen:** On-Demand State Repartitioning, spark.sql.streaming.stateStore.partitions, RocksDB State Store, controlBatch.REPARTITION Metrik, Checkpoint-Kompatibilität bei Structured Streaming
   - **Zusammenfassung:** Stateful Streaming-Queries in Spark waren bisher an eine beim Start festgelegte Partitionsanzahl gebunden, da eine spätere Änderung den Checkpoint und damit den gespeicherten Zustand unbrauchbar gemacht hätte. Databricks stellt mit dem On-Demand State Repartitioning eine neue Public-Preview-Funktion vor, mit der sich die Partitionierung von RocksDB-basierten State Stores über einen gezielten Neustart der Query anpassen lässt, ohne den Checkpoint zu verwerfen. Ein einmaliger Kontroll-Batch verteilt dabei alle Zustandsschlüssel korrekt auf das neue Partitionslayout, der Fortschritt lässt sich über eigene Metriken beobachten. Als Praxisbeispiel wird Coveo genannt, das durch dynamische Anpassung der Partitionsanzahl deutliche Einsparungen bei Speicherkosten erzielte. Damit wird aus einer bisher fixen Architekturentscheidung ein operativer Hebel für Nachjustierung im laufenden Betrieb.

[From Events to Insights: Complex State Processing with Schema Evolution in transformWithState](https://www.databricks.com/blog/events-insights-complex-state-processing-schema-evolution-transformwithstate) — 2025-12-01
   - **Themen:** transformWithStateInPandas, Schema Evolution im Streaming-State, Type Widening, Avro-Encoding, RocksDB State Store
   - **Zusammenfassung:** Ändert sich in einer Streaming-Anwendung das Datenschema, führte das bisher häufig dazu, dass gespeicherter Zustand nicht mehr zum neuen Format passt und aufwendig migriert oder verworfen werden musste. Der Artikel stellt vor, wie die transformWithStateInPandas-API in Spark 4.0 automatische Schema-Evolution ermöglicht, sodass sich Zustandsvariablen zwischen Versionen einer Streaming-Query ändern lassen, etwa durch neue Felder oder breitere Datentypen, ohne bestehende Sitzungsdaten zu verlieren. Voraussetzung dafür sind Avro-Serialisierung und ein RocksDB-basierter State Store; anhand eines Beispiels zur Sitzungsverfolgung in einem Onlineshop wird gezeigt, wie ältere Sitzungen automatisch auf ein erweitertes Schema angehoben werden. Dadurch lassen sich neue Tracking-Funktionen mit minimalen Unterbrechungen einführen, während die historische Kontinuität für Analysen erhalten bleibt.

[Continuous Environmental Monitoring Using the New transformWithState API](https://www.databricks.com/blog/continuous-environmental-monitoring-using-new-transformwithstate-api) — 2025-07-30
   - **Themen:** transformWithState API (Spark 4.0), ValueState, ListState, MapState, State TTL (Time-to-Live), State Reader API, transformWithStateInPandas
   - **Zusammenfassung:** Der Artikel behandelt das Problem, dass klassische zustandslose Streaming-Verarbeitung nicht ausreicht, um komplexe Szenarien wie kontinuierliches Umweltmonitoring mit historischen Trends und Mustererkennung über viele Sensoren hinweg abzubilden. Als Lösung wird die neue transformWithState-API von Apache Spark 4.0 vorgestellt, die gegenüber älteren zustandsbehafteten APIs wie mapGroupsWithState und flatMapGroupsWithState erweiterte Möglichkeiten bietet, etwa typisierte Zustandsobjekte für Einzelwerte, geordnete Listen und Schlüssel-Wert-Zuordnungen sowie automatisches Verfallen alter Zustände über TTL. Anhand von Beispielen zur Schwellenwertüberwachung, Mustererkennung über die Zeit und ortsbezogener Auswertung zeigt der Beitrag, wie sich damit robuste Streaming-Pipelines für Sensordaten bauen lassen. Der zentrale Mehrwert liegt darin, dass Entwickler nun deutlich flexibler und mit besserer Debugging-Unterstützung anspruchsvolle zustandsbehaftete Streaming-Anwendungen umsetzen können, ohne auf externe Datenbanken angewiesen zu sein.

[Announcing the State Reader API: The New "Statestore" Data Source](https://www.databricks.com/blog/announcing-state-reader-api-new-statestore-data-source) — 2024-03-28

   - **Zusammenfassung:** Der Beitrag beschreibt, dass Entwickler zustandsbehafteter Structured-Streaming-Anwendungen bislang auf umfangreiches Logging und die Analyse von Executor-Logs angewiesen waren, um interne Zustände zu verstehen, was Entwicklung, Tests und Produktionsfehlersuche erschwerte. Mit Databricks Runtime 14.3 wird die neue State Reader API vorgestellt, die es erlaubt, den internen Zustand einer Streaming-Anwendung direkt als Datenquelle abzufragen, etwa über ein Format für Metadaten zum Zustandsspeicher und ein weiteres für die eigentlichen Schlüssel-Wert-Paare. Damit lassen sich etwa Duplikaterkennung mit Wasserzeichen oder gruppierte Zustandsoperationen gezielt untersuchen, ohne zusätzlichen Debug-Code einzubauen. Das zentrale Ergebnis ist eine deutlich einfachere und direktere Möglichkeit, interne Streaming-Zustände zu inspizieren und dadurch Entwicklung sowie Fehleranalyse erheblich zu beschleunigen.

Insgesamt sinken dadurch Latenz und Ressourcenverbrauch zustandsbehafteter Pipelines spürbar, verfügbar ab Databricks Runtime 13.3 LTS.

Anhand ausführlicher Benchmarks vergleicht der Beitrag die neue Implementierung mit dem älteren HDFS-basierten Ansatz und zeigt deutliche Verbesserungen bei den Perzentil-Latenzen für verschiedene Operationstypen. Das zentrale Ergebnis ist eine bis zu drei- bis vierfache Latenzverbesserung bei Hochdurchsatz-Workloads ab Databricks Runtime 13.3 LTS, wodurch mehr Echtzeit-Anwendungsfälle praktikabel werden.

### 1.3 Structured-Streaming-Grundlagen, Produktion und Monitoring

[Structured Streaming: A Year in Review](https://www.databricks.com/blog/2022/02/07/structured-streaming-a-year-in-review.html) — 2022-02-07
   - **Themen:** Asynchrones Checkpointing, flatMapGroupsWithState mit Initial State, Native Session Windows, StreamingQueryProgress-Backpressure-Metriken, Delta-Live-Tables-Autoscaling und Trigger.AvailableNow
   - **Zusammenfassung:** Der Rückblick fasst zusammen, wie im Jahresverlauf drei zentrale Probleme von Structured Streaming angegangen wurden: hohe Latenz bei zustandsbehafteten Operationen, mangelnde Beobachtbarkeit von Streaming-Workloads und ineffiziente Ressourcenzuteilung. Als Lösungen werden asynchrones Checkpointing, verbesserte zustandsbehaftete Operatoren mit Unterstützung für einen initialen State sowie native Session-Windows vorgestellt, dazu erweiterte Fortschrittsmetriken wie Backpressure-Werte für Kafka, Kinesis und Auto Loader sowie ein intelligentes Autoscaling für Delta Live Tables auf Basis dieser Metriken. Der neue Trigger-Typ AvailableNow ermöglicht zudem die Verarbeitung aller verfügbaren Daten in mehreren kontrollierten Batches. Ergebnis ist eine insgesamt reifere, produktionstauglichere Streaming-Plattform mit geringerer Latenz und besserer Kosteneffizienz.


[A look at the new Structured Streaming UI in Apache Spark 3.0](https://www.databricks.com/blog/2020/07/29/a-look-at-the-new-structured-streaming-ui-in-apache-spark-3-0.html) — 2020-07-29
   - **Themen:** Structured Streaming UI, Input Rate/Process Rate Metriken, Batch Duration, addBatch/getOffset/walCommit-Phasen, Spark 3.0 Monitoring
   - **Zusammenfassung:** Der Artikel beschreibt, dass es für Structured-Streaming-Jobs im Gegensatz zum klassischen DStream-basierten Spark Streaming bislang keine vergleichbare grafische Überwachungsoberfläche gab, was Produktionsbetrieb und Fehlersuche erschwerte. Apache Spark 3.0 führt daher eine neue UI ein, die aggregierte Statistiken wie Laufzeitstatus und Batch-Kennzahlen sowie detaillierte Metriken zu Input- und Verarbeitungsrate, Batchdauer und Latenz visualisiert und dabei interne Phasen wie addBatch, getOffset oder walCommit einzeln aufschlüsselt.

# Generated Columns

Generated Columns berechnen und speichern automatisch Werte, die von Ausdrücken abgeleitet werden, die andere Tabellenspalten referenzieren. „Wird ohne Werte für Generated Columns in eine Tabelle geschrieben, berechnet Delta Lake diese automatisch." Diese Spalten werden physisch in den zugrunde liegenden Datendateien gespeichert, nicht zur Query-Zeit berechnet. Basierend auf der offiziellen Databricks-Doku-Seite.

## 1. Grundsyntax

```sql
CREATE TABLE default.people10m (
  id INT,
  firstName STRING,
  birthDate TIMESTAMP,
  dateOfBirth DATE GENERATED ALWAYS AS (CAST(birthDate AS DATE))
);
```

```python
DeltaTable.create(spark) \
  .tableName("default.people10m") \
  .addColumn("id", "INT") \
  .addColumn("birthDate", "TIMESTAMP") \
  .addColumn("dateOfBirth", DateType(),
    generatedAlwaysAs="CAST(birthDate AS DATE)") \
  .execute()
```

## 2. Unterstützte Ausdrücke

Erlaubt: arithmetische Operationen (`base_price * 1.1`), String-Funktionen (`CONCAT(first_name, ' ', last_name)`, `SUBSTRING(col, 1, 3)`), Datumsfunktionen (`CAST(birthDate AS DATE)`, `YEAR(eventTime)`).

**Nicht unterstützt:** benutzerdefinierte Funktionen, Aggregatfunktionen, Window-Funktionen und Multi-Row-Funktionen.

## 3. Anwendungsfall: automatische Partitionsfilter-Generierung

Bei Partitionierung nach Generated Columns leitet Delta Lake automatisch Filter aus Queries auf der Basisspalte ab:

```sql
CREATE TABLE events(
  eventId BIGINT,
  eventTime TIMESTAMP,
  eventDate DATE GENERATED ALWAYS AS (CAST(eventTime AS DATE))
)
PARTITIONED BY (eventDate);

-- Query ohne expliziten Partitionsfilter:
SELECT * FROM events
WHERE eventTime >= "2020-10-01" AND eventTime <= "2020-10-01 12:00:00"
-- Filtert automatisch die Partition date=2020-10-01
```

**Unterstützte Partitionsausdrücke:** `CAST(col AS DATE)` (aus TIMESTAMP), `YEAR()`/`MONTH()`/`DAY()`/`HOUR()`-Kombinationen, `SUBSTRING(col, pos, len)` (aus STRING), `DATE_FORMAT(col, format)` mit den Mustern `yyyy-MM`, `yyyy-MM-dd-HH`, `yyyy-MM-dd`. Auf Databricks Runtime 10.4 LTS und darunter ist dafür Photon erforderlich; ab Runtime 11.3 LTS nicht mehr.

## 4. Identity Columns (spezialisierte Generated Columns)

Erzeugen eindeutige, inkrementierende Werte je eingefügtem Datensatz:

```sql
CREATE TABLE table_name (
  id_col1 BIGINT GENERATED ALWAYS AS IDENTITY,
  id_col2 BIGINT GENERATED ALWAYS AS IDENTITY (START WITH -1 INCREMENT BY 1),
  id_col3 BIGINT GENERATED BY DEFAULT AS IDENTITY
);
```

```python
from delta.tables import DeltaTable, IdentityGenerator
from pyspark.sql.types import LongType

DeltaTable.create() \
  .tableName("table_name") \
  .addColumn("id_col1", dataType=LongType(), generatedAlwaysAs=IdentityGenerator()) \
  .addColumn("id_col2", dataType=LongType(), generatedAlwaysAs=IdentityGenerator(start=-1, step=1)) \
  .addColumn("id_col3", dataType=LongType(), generatedByDefaultAs=IdentityGenerator()) \
  .execute()
```

Startwert und Schrittweite sind anpassbar (Standard beider: 1, Schrittweite darf positiv oder negativ, aber nicht 0 sein). `GENERATED ALWAYS` verhindert manuelles Überschreiben; `GENERATED BY DEFAULT` erlaubt es. Identity Columns unterstützen **ausschließlich den Typ `BIGINT`**; Werte sind eindeutig, aber **nicht garantiert lückenlos fortlaufend**. Python-/Scala-APIs dafür sind ab Databricks Runtime 16.0 verfügbar.

**Einschränkungen:** deaktiviert nebenläufige Transaktionen, keine Partitionierung, keine `ALTER`-Modifikationen zum Hinzufügen/Ersetzen/Ändern von Identity Columns, keine Aktualisierung bestehender Werte (nur Löschen + Neueinfügen), keine Definition über `CTAS`-Statements, Fehler bei Überschreitung des `BIGINT`-Wertebereichs.

**Workaround für Migrationen mit vorhandenen IDs:** Da `CTAS` keine Identity Columns definieren kann, lässt sich stattdessen die Zieltabelle vorab mit `CREATE OR REPLACE TABLE` samt Identity Column anlegen — bestehende IDs übernimmt man per expliziter `INSERT INTO`-Spaltenliste, neue Datensätze lässt man die ID automatisch generieren:

```sql
CREATE OR REPLACE TABLE new_table (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY (START WITH 5),
  event_date DATE,
  some_value BIGINT);

-- Bestehende IDs aus der alten Tabelle übernehmen
INSERT INTO new_table (id, event_date, some_value)
SELECT id, event_date, some_value FROM old_table;

-- Neue Datensätze einfügen und IDs automatisch generieren lassen
INSERT INTO new_table (event_date, some_value)
SELECT event_date, some_value FROM new_records;
```

## 5. Constraints und Interaktionen

**Validierungsanforderung:** Übergebene Werte müssen `(<value> <=> <generation expression>) IS TRUE` erfüllen, sonst schlägt der Schreibvorgang fehl.

**Inkompatibilität mit Column Masks:** Generated Columns können keine maskierten Spalten referenzieren und umgekehrt — das führt zu Fehlern, die die Query-Ausführung verhindern.

```sql
-- Fehler: Generated Column referenziert eine maskierte Spalte direkt bei der Tabellenerstellung
CREATE TABLE tbl (
  a INT MASK masking_function,
  generated_col INT GENERATED ALWAYS AS (a + 1)) USING DELTA;
```

```sql
-- Fehler: Maske wird nachträglich auf eine bereits von einer Generated Column referenzierte Spalte gesetzt
CREATE TABLE tbl (
  a INT,
  generated_col INT GENERATED ALWAYS AS (a + 1)) USING DELTA;
ALTER TABLE tbl ALTER COLUMN a SET MASK masking_function;
```

**Protokoll-Hinweis:** Die Aktivierung von Generated Columns hebt das Tabellen-Writer-Protokoll an, was die Kompatibilität mit externen Delta-Lake-Clients beeinträchtigen kann.
